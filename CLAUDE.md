# Backend (NestJS)

NestJS 11 + Zod v4 + `nestjs-zod` v5. No `class-validator` / `class-transformer` — Zod is the single source of truth for validation, types, and Swagger schemas.

## Request → response pipeline

Wired once globally in `src/app.module.ts` — never repeat per-controller:

1. `ZodValidationPipe` (APP_PIPE) — parses `@Body()`, `@Query()`, `@Param()` against the Zod DTO. Failure → `ZodValidationException`.
2. Controller handler runs.
3. `ZodSerializerInterceptor` (APP_INTERCEPTOR) — re-validates the return value against the response DTO declared by `@ZodResponse({ type })`.
4. `WebResponseExceptionFilter` (APP_FILTER) — converts any thrown error into the `WebResponse` envelope.

Swagger is generated by `SwaggerModule.createDocument` and post-processed with `cleanupOpenApiDoc()` in `src/main.ts`. The `@nestjs/swagger` CLI plugin is enabled in `nest-cli.json` but is a no-op for Zod DTOs — `@ZodResponse` is what produces their OpenAPI schemas.

## Response envelope

Every successful response: `{ data, paging? }`. Every error: `{ errors: "..." }`. Defined in `src/common/web-response.ts`.

- `WebResponseDto(schema)` — wraps a single-item schema as a DTO class.
- `WebResponseListDto(schema)` — wraps `z.array(schema)` as a DTO class.
- `paginated(items, query, total)` — builds `{ data, paging }` for list endpoints. Don't inline paging math.
- `paginationQuerySchema` — shared `{ limit, offset }` query schema. Extend it for filters: `paginationQuerySchema.extend({ status: z.string().optional() })`.

## Per-resource layout

Four files. Don't split schemas from DTOs.

```
src/<resource>/
  <resource>.dto.ts         schemas + Cat-style type alias + DTO classes
  <resource>.service.ts
  <resource>.controller.ts
  <resource>.module.ts
```

Recipe for `cats.dto.ts`:

```ts
export const CatSchema = z.object({ id: z.uuid(), name: z.string().min(1), /* ... */ });
export type Cat = z.infer<typeof CatSchema>;

export class CreateCatDto extends createZodDto(CatSchema.omit({ id: true })) {}
export class UpdateCatDto extends createZodDto(CatSchema.omit({ id: true }).partial()) {}
export class ListCatsQueryDto extends createZodDto(paginationQuerySchema) {}

export class CatResponseDto extends WebResponseDto(CatSchema) {}
export class CatListResponseDto extends WebResponseListDto(CatSchema) {}
```

Controller pattern — one `@ZodResponse` per route, explicit `WebResponse<T>` return type:

```ts
@Get()
@ZodResponse({ type: CatListResponseDto })
list(@Query() q: ListCatsQueryDto): WebResponse<Cat[]> {
  const { items, total } = this.catsService.list(q.limit, q.offset);
  return paginated(items, q, total);
}

@Get(':id')
@ZodResponse({ type: CatResponseDto })
get(@Param('id', ParseUUIDPipe) id: string): WebResponse<Cat> {
  return { data: this.catsService.get(id) };
}
```

## Conventions and gotchas

- **`import type` for type-only symbols in decorated signatures.** `Cat`, `WebResponse`, etc. used in `@ZodResponse`-decorated method return types must be type-only imports. Otherwise `isolatedModules + emitDecoratorMetadata` emits broken runtime metadata, and you'll see misleading lints like "Unsafe assignment of an error typed value" or compiler error TS1272.
- **`z.uuid()`, not `z.string().uuid()`.** Zod v4 deprecates the chained form.
- **Throw `HttpException` subclasses from services** (e.g. `NotFoundException`). The filter unwraps them into `{ errors: message }` with the correct status code.
- **Validation errors are flattened to a single string** in the `errors` field (`path: message; path: message`). If you ever need structured issues for client localization, change `errors?: string` in `web-response.ts` to accept an array.
- **Don't wrap responses with a custom interceptor.** The envelope is built explicitly in handlers so the OpenAPI schema (`CatResponseDto_Output`, etc.) stays accurate.
- **Don't add `@ApiProperty()` to Zod DTO classes.** The schema is the metadata.
- **Service return types are domain types**, not DTOs. The DTO is the wire contract; the service speaks `Cat`, not `CatResponseDto`.

## Environment configuration

Defined in `src/common/env.config.ts`. Zod is the single source of truth for env vars too.

- `envSchema` — Zod schema for every variable, with `z.coerce.number()` for numerics and string-to-bool transforms for flags.
- `env` — eagerly validated `envSchema.parse(process.env)`. On failure, the process exits with a flattened error payload **before Nest boots**.
- `DATABASE_URL` — derived from `DB_*` vars. Used by `drizzle.config.ts` and the script helpers (`src/db/scripts/helpers.ts`).
- `ConfigModule.forRoot({ validate: (raw) => envSchema.parse(raw) })` is registered in `AppModule` so `ConfigService.get()` returns validated, transformed values too.

**Direct import is preferred** over `ConfigService` — it's typed end-to-end:

```ts
import { env } from '../common/env.config';

if (env.NODE_ENV === 'production') { /* ... */ }
```

Add new vars by extending `envSchema` and updating `.env.example`. Don't read `process.env` directly anywhere else.

## Database (Drizzle ORM)

PostgreSQL via `drizzle-orm` + `postgres-js`. The runtime entry point is `src/common/drizzle.service.ts` (`DrizzleService`) — Nest-managed. Inject it in services: `constructor(private drizzle: DrizzleService)` then `this.drizzle.db.select().from(...)`. Lifecycle-managed: opens on `onModuleInit` (with `SELECT 1` healthcheck), closes on `onModuleDestroy`.

`DrizzleService` is provided by `@Global() CommonModule`, so any service can inject it without importing `CommonModule` again.

Standalone scripts (`src/db/scripts/*.ts`) build their own short-lived connection through helpers — they don't share the Nest pool.

### Schema layout

```
src/db/
  schema/
    index.ts                  barrel — re-export every table & relations file
    timestamps.ts             shared { created_at, updated_at, deleted_at } + notDeleted()
    <domain>.ts               one file per table
    relations.ts              cross-table relations
  migrations/                 generated by drizzle-kit (do not edit)
  seeds/
    <name>.ts                 one file per seed (idempotent), called directly from scripts/seed.ts
  scripts/
    helpers.ts                scriptLogger + adminConnection / appConnection / withDb / confirm / runScript
    migrate.ts                auto-creates DB in dev, applies pending migrations
    reset.ts                  confirms then DROPs the DB
    seed.ts                   runs system or test seeds (dispatches on argv)
```

Every domain table:

```ts
import { pgTable, uuid, varchar, index } from 'drizzle-orm/pg-core';
import { timestamps, notDeleted } from './timestamps';

export const users = pgTable(
  'users',
  {
    id: uuid('id').primaryKey().defaultRandom(),
    email: varchar('email', { length: 255 }).notNull(),
    ...timestamps,
  },
  (t) => [index('users_email_idx').on(t.email)],
);
export type User = typeof users.$inferSelect;
```

Then re-export from `src/db/schema/index.ts` so `DrizzleService` picks it up.

### Soft delete

`timestamps` includes `deleted_at: bigint`. Always filter active rows with `notDeleted(table)`:

```ts
import { notDeleted } from '../db/schema/timestamps';
await this.drizzle.db.select().from(users).where(notDeleted(users));
```

### Migrations and seeds

```bash
npm run orm:create        # generate SQL from schema diff into src/db/migrations
npm run orm:up            # auto-create DB in dev, then apply pending migrations
npm run orm:check         # validate migrations folder
npm run orm:studio        # drizzle-kit studio
npm run orm:seed          # run system seeds (required for the platform)
npm run orm:seed:test     # run test seeds (fake data for dev)
npm run orm:fresh         # confirm + drop DB, then orm:up && orm:seed
```

System and test seeds are kept distinct on purpose — there's no "seed everything" script. If you want test data after `orm:fresh`, run `npm run orm:seed:test` separately.

Nothing runs automatically at boot. Migrations and seeds are explicit:

- **`orm:up`** uses `src/db/scripts/migrate.ts` (run via `tsx`). In dev (`NODE_ENV=development`), it connects to the cluster's `postgres` admin database and `CREATE DATABASE` if `env.DB_NAME` is missing — so a fresh clone can run `npm run orm:up` without manually creating the DB. In other environments it skips the create step and only applies migrations.
- **`orm:fresh`** is the dev reset button. It runs `reset.ts` (which prompts before `DROP DATABASE`), then `orm:up`, then `orm:seed` (system only).

### Seeds

Each seed file in `src/db/seeds/<name>.ts` exports a default async function `(db: SeedDb) => Promise<void>` and **must be idempotent**. Import `scriptLogger` and `SeedDb` from `../scripts/helpers`:

```ts
import { someTable } from '../schema';
import { scriptLogger, type SeedDb } from '../scripts/helpers';

export default async function seed(db: SeedDb): Promise<void> {
  const existing = await db.select({ key: someTable.key }).from(someTable);
  const existingKeys = new Set(existing.map((r) => r.key));
  const toInsert = items.filter((i) => !existingKeys.has(i.key));
  if (toInsert.length === 0) {
    scriptLogger.log('Already seeded, skipping.');
    return;
  }
  await db.insert(someTable).values(toInsert);
  scriptLogger.log(`Inserted ${toInsert.length} rows.`);
}
```

Then add a direct import in [seed.ts](src/db/scripts/seed.ts) and call it inside the `target === 'system'` or `else` (test) branch (system = required for the platform, test = fake data for dev). The included [test-user.ts](src/db/seeds/test-user.ts) demonstrates the pattern.
